## Problem

Need a way to manually classify mutants based on their priority for identifying insufficiently tested code regions (hotspots). This supports two workflows:
1. Test writing: Where should we add tests to get the biggest impact?
2. Bug hunting: Where should we look for bugs in undertested code?

Current schema doesn't support storing these classifications or relationships between equivalent mutants. This is particularly important for AI agent workflows that analyze mutation testing results and need to efficiently communicate findings to subsequent agents.

## Solution

Add a new `triage` table to track per-mutant priority classifications and relationships, enabling hotspot identification that's useful for both test writing and bug hunting.

## Schema

```sql
CREATE TABLE triage (
    id INTEGER PRIMARY KEY,
    mutant_id INTEGER NOT NULL UNIQUE,
    status TEXT NOT NULL,  -- 'todo', 'duplicate', 'redundant', 'high_priority', 'medium_priority', 'low_priority'
    related_mutants TEXT,  -- JSON array: "[123, 124, 125]"
    notes TEXT,            -- Optional freeform explanation (no length limit)
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    FOREIGN KEY (mutant_id) REFERENCES mutants(id) ON DELETE CASCADE
);

CREATE INDEX idx_triage_mutant_id ON triage(mutant_id);
CREATE INDEX idx_triage_status ON triage(status);
```

## Triage Status Values

- `todo` (default when no DB record exists) - Not yet triaged
- `duplicate` (skip testing) - Equivalent to other mutant(s), references them via related_mutants
- `redundant` (skip testing) - Inherently not useful (e.g., `> 0` → `!= 0` for unsigned)
- `high_priority` - Critical hotspot indicator (important code, high TCAP, or high-severity mutation)
- `medium_priority` - Useful hotspot indicator
- `low_priority` - Minor hotspot indicator

## Priority Determination

Priority is a human/AI judgment that synthesizes multiple factors:
- **TCAP value**: Higher TCAP suggests more important test gaps
- **Mutation severity**: High-severity mutations (errors, missing logic) indicate bigger gaps
- **Code importance**: Auth/security code more critical than logging utilities
- **Other context**: Domain knowledge, recent changes, production issues, etc.

This is intentionally fuzzy - better suited to agent/human judgment than automation. The triage system stores the decision and optional notes explaining the reasoning.

Note: "Mutation severity" (high/med/low) is a type-level property of mutations (what kind of change). "Mutant priority" (high/med/low) is an instance-level triage decision for specific mutants. These are related but distinct concepts.

## Related Mutants Field

Can be populated for any status where relationships matter:
- `duplicate`: List of equivalent mutants (mark N-1 as duplicate, leave 1 as todo/priority)
- `high_priority`: Can link related high-priority mutants to group hotspots
- `medium_priority`, `low_priority`: Same grouping capability
- `redundant`: Optional grouping of redundant variations

## CLI Commands

```bash
# Triage single or multiple mutants (per-mutant only, no bulk by target/type)
mewt triage --mutants 123,124,125 --status high_priority --notes "auth logic gap"
mewt triage --mutants 126 --status duplicate --related 123,124,125
mewt triage --mutants 127 --status redundant --notes "unsigned int comparison"

# Filter in existing commands
mewt print mutants --triage-status high_priority,medium_priority
mewt print mutants --triage-status todo  # show untriaged only
```

## Behavior

- **Lazy creation:** Triage records only created when explicitly set via CLI
- **In-memory default:** When no DB record exists, use `status='todo'` in memory for display
- **Cascade delete:** When mutant deleted, triage record auto-deleted via FOREIGN KEY ON DELETE CASCADE
- **Foreign key validation:** All mutant IDs in `related_mutants` must reference existing mutants
- **One record per mutant:** `UNIQUE(mutant_id)` constraint, updates replace existing record
- **Notes are optional:** Users encouraged but not required to provide notes

## Default `mewt run` Behavior

- **Test these statuses:** `todo`, `high_priority`, `medium_priority`, `low_priority`
- **Skip these statuses:** `duplicate`, `redundant`
- **Override:** Use existing `--comprehensive` flag to test everything regardless of triage

**For duplicate handling:** Mark the mutants you DON'T want to test as `status=duplicate` with `related_mutants` pointing to the canonical one. Leave the canonical mutant as `todo` or a priority status. This ensures only one mutant from an equivalence group is tested.

## Integration Points

1. **`mewt status`**: Add triage breakdown per target (not in campaign total):
   ```
   Target: src/foo.rs
     Mutants: 100
     ...existing stats...
     Triage: 60 todo, 20 high_priority, 10 medium_priority, 5 low_priority, 3 duplicate, 2 redundant
   ```

2. **`mewt print mutants`**: Add `--triage-status` filter (no display changes needed)

3. **`mewt run`**: Skip duplicate/redundant by default; use `--comprehensive` to include all

4. **`mewt clean`**: Cascade deletion handles cleanup automatically

## Migration

- New table, no existing data migration needed
- Migration file: `migrations/NNN_add_triage_table.sql`
- SQLite's TEXT type supports arbitrarily long notes (no practical limit for our use case)

## Implementation Notes

- Mutants referenced in `related_mutants` are protected by foreign key constraints - they cannot be deleted while referenced, preventing orphaned references
- Pre-campaign triage is supported - mutants can be triaged before testing
- The distinction between mutation severity (type-level) and mutant priority (instance-level) should be clear in user-facing documentation and help text
- Related mutants can be useful for any status, not just duplicates - e.g., grouping multiple high-priority mutants that indicate the same hotspot
